Determination
"No — this must be fixed in codegen." TAST-level constraint rewriting is technically possible but not supported and not safe for the realsig+ class?method case. The substitution must be performed in IlxGen.fs at the point of IL generic-parameter emission.
Justification (based on verified compiler structure)
1. Typar identity — stamp-based substitution is the model, and it's sufficient to find the targets
- A Typar is identified by typar_stamp (TypedTree.fs:2424–2445, accessor at :2456–2457); Stamp = int64 (TypedTree.fs:39); equality is typarEq = (tp1.Stamp = tp2.Stamp) (TypedTreeBasics.fs:88).
- Every substitution map in the compiler is stamp-keyed (StampMap<'T>, TyparMap<'T> at TypedTreeOps.Remap.fs:79–103). So matching on stamp to locate "the class typar" inside a constraint is well-defined and already the compiler's own model.
- Conclusion for Q1: stamp-based substitution is sufficient and unambiguous for identifying replacement sites. This part is not in question.
2. Constraint representation — constraints are TType trees that can be walked
- TyparConstraint (TypedTree.fs:2670–2712) stores its type payloads as TType/TType list by value: CoercesTo of TType, DefaultsTo of int*TType, IsEnum of TType, IsDelegate of TType*TType, SimpleChoice of TTypes, MayResolveMember of TTrait(TTypes,TTypes,TType ...).
- A typar appearing inside a constraint is a TType_var(ty, nullness) node (TypedTree.fs:4680).
- There is a purpose-built, working constraint rewriter: remapTyparConstraintsAux (TypedTreeOps.Remap.fs:305–324) walks each constraint and runs remapTypeAux over the embedded TType(s) — it is the exact function needed to substitute typars inside a TType_var.
- Public wrappers exist: instType (Remap.fs:516–526), instTyparConstraints (Remap.fs:534–538).
- Conclusion for Q2: the constraints are storable-rewritable TType trees containing Typar nodes, and the compiler already has a remapTyparConstraintsAux that does precisely this walk. Representation-wise, substitution is expressible.
3. Phase correctness — TLR is the wrong phase; this is the decisive point
This is where the "supported and safe" answer must be rejected.
a) The realsig+ closure carries the original class typar — there is no clean "class typar ? method typar" pair to substitute into.
- In realsig+, the lifted helper keeps the class's typars (they are prepended into fHat as newTps = envp.ep_etps @ tps at InnerLambdasToTopLevelFuncs.fs:868 and :1050), and crucially the closure captures class values by reference; their v.Type and the carried typars are the same Typar instances (e.g. mkCompGenLocal env.m v.LogicalName v.Type at :792); the typar_astype cache is shared (TypedTreeBasics.fs:228 note; tp.AsType caches on the typar and is not refreshed by copyTypar because copyTypar sets typar_astype = defaultof<_> at :228 — cached TTypes that already point at the original typar are not touched).
- Under realsig- the class typars are not the method's typars at all — the helper is homed on the module, and the "method typar" is created lazily by the only typar-clone site in the pipeline, copyAndRemapAndBindTyparsFull (Remap.fs:382–415), whose DEBUG trace explicitly labels it "class-env -> method-env remap" (Remap.fs:396–411) and which already calls remapTyparConstraintsAux + SetConstraints. That code path is the intended, supported place where class?method constraint remap happens.
b) The TAST is no longer the checker's source of truth at this depth.
- The TLR pass rewrites expressions (it inserts pack/unpack closures, mkInvisibleBind, new fHat vals at :800–808, :879). The type information those new values carry is consumed by IlxGen, which reconstructs the IL method signature and re-derives constraints from the method's actual parameter list.
- The constraint set on a typar is stable post-check, but the constraint types are only well-formed relative to the typars that are formally bound in scope. Under realsig+, the lifted helper's bound typars are the class's, so the embedded TType_vars that would reference the method typar do not yet exist as bound typars in the TAST you'd be editing. Substituting the class typar out of them would produce dangling typar references (a TType_var pointing at a typar that is not Typar-bound in the method) — invalid IL metadata, exactly the reported bug, re-introduced by the rewrite.
- The checker's semantic assumptions (constraints well-scoped over the bound typars, typarEq/stamp identity as the equivalence relation, remapTypeAux assuming the tpinst domain is a set of bound typars) are not preserved by a post-hoc rewrite after the closure has been emitted and after val/fHat types have been repackaged.
c) The "copy + remap constraints" mechanism already exists and is already in use for the legal direction, which actually argues the realsig+ case is not a legal TAST transform at all.
- copyAndRemapAndBindTyparsFull (Remap.fs:382–415) is the only sanctioned typar-clone-and-constrain-remap, and it operates on TType_forall bound typars during remapTypeFull. The TLR pass never invokes this for realsig+ — it relies on the fact that under realsig+ the class typars are the helper's bound typars. That is a deliberate representation choice, not a missing rewrite that can be papered over. Forcing a rewrite after the fact would fight the representation, not join it.
- The DEBUG instrumentation at Remap.fs:396–411 ("class-env -> method-env remap", constraintStampsBefore/After) and at TypedTree.fs:2554–2575 (SetConstraints provenance trace) show the team has already tried to reason about constraint provenance at the TAST boundary — and the correct boundary they chose is inside remapTypeFull (a TAST walk where the bound typars are in scope), not in the post-lambda TLR pass.
d) The checker is a single-pass typechecker; there is no "rewire constraints" pass between check and IL emission. Post-check the TAST is treated as invariant input to the optimizer and to IlxGen. Every rewrite pass in Optimize/ (TLR, Optimizer.fs) operates on TypedPar/expressions with `TType invariance assumed. IlxGen is the single consumer that must honor the actual IL generic parameters.
So to answer Q3–Q4 directly:
- Q3 — Phase: TLR (InnerLambdasToTopLevelFuncs.fs) is not the right place. It is too late to do a safe Typar ? Typar constraint rewrite that keeps well-scopedness, because the realsig+ representation intentionally shares the class typars with the helper and repackages the fHat type with those same typars.
- Q4 — Semantic invariants: A pure "class typar ? method typar" alpha-renaming inside TType_vars would be a semantic alpha-rename if and only if the method typar is actually a bound quantifier of the helper. In the realsig+ representation the helper's bound typars are the class's, and the "method typar" that IlxGen will emit is a fresh quantifier derived by the IL generator, not a TAST typar. Rewriting the TAST's constraints to point at a typar that is not (yet) a bound quantifier of the TAST node you're editing would break the checker's invariants (well-scopedness, typarEq identity as the equivalence, constraint-solver solution tables keyed by original stamps, TraitConstraintInfo solution cells that are keyed by the original typar). remapTraitInfo (Remap.fs:326–371) — used by remapTyparConstraintsAux for MayResolveMember — recreates TTrait solution cells; doing that post-check, after trait solutions have been resolved by ConstraintSolver.fs (see instTyparConstraints call at ConstraintSolver.fs:4531–4542), would orphan the solver's solution tables. That is a semantic violation, not a harmless alpha-rename.
Conclusion: TAST-level rewriting is syntactically available (remapTyparConstraintsAux exists) but not semantically supported at this point in the pipeline for the realsig+ class?method case. The representation the TLR pass relies on (shared class typars, repackaged fHat type) is itself the thing that makes the method typar's constraint "point to the class typar" — the correct fix is to make IlxGen emit the method typar's constraints in terms of the method's own quantifier.
The correct codegen fix (IlxGen.fs)
The bug is that IlxGen emits the method's GenericParameter with its constraint list copied from the Typar.Constraints (which, under realsig+, still reference the class typar via TType_var). The fix is a localized rewrite at IL emission time, after the method's own quantifier has been materialised.
Where the constraint is read for IL emission:
The constraint payload is a TType tree (see TyparConstraint.CoercesTo(ty, range), TypedTree.fs:2673). IlxGen walks these into MetadataBuilder constraint definitions. To fix, at the moment it builds the GenericParameter's GenParamConstraint:
// Pseudocode sketch for the IlxGen-side fix at the emission point:
// given (mtp: Typar) the method's own fresh quantifier and
// (ctps: Typar list) the class typars that the constraint payload may still name,
let substClassTypars mtp ctps ty =
    let renames = List.zip ctps (List.map (fun mtp -> TType_var(mtp, nullnessFree)) ctps)  // or: a TyparMap
    // walk the TType tree substituting any TType_var(tp, _) where tp in ctps with TType_var(mtp, ...)
    remapType (mkRemapWithTyparInst renames) ty
Concrete steps:
1. Identify the mapping. When IlxGen builds a generic method on a type whose own typars are ctps and the method's own fresh typar is mtp, the correct constraint is "class typar ? method typar" substitution inside the constraint payload only. The mapping is ctps ? [mtp]-paired (for the single-parameter case) or ctps[i] ? mtp[i] for the multi case. Use instTyparConstraints-style rewriting (remapTyparConstraintsAux) on the payload only, building the method typar's fresh TType_var.
2. Build the method typar first. Ensure mtp is a genuine Typar.New with typar_stamp = newStamp() (i.e. a distinct identity) and that the constraint rewrite is performed for the method's emission, not stored back onto the Typar object. This preserves the checker's invariants: the Typar.Constraints field still points to the class typar (unchanged), and the rewrite happens on the wire to the metadata builder.
3. Reconstruct the constraint type at emission time. For TyparConstraint.CoercesTo(ty, range) (and IsEnum, IsDelegate, DefaultsTo, SimpleChoice, MayResolveMember), run remapTypeAux (or the instType equivalent) with a one-element tpinst of (classTypar, TType_var(mtp, nullnessFree)) to produce a TType whose TType_vars name the method typar. Then convert that rewritten TType into the IL constraint signature.
4. Do not call Typar.SetConstraints. Calling SetConstraints on the class typar to point it at the method typar would corrupt the class's own constraints (used by other members, used by ConstraintSolver.fs, keyed by the original stamps). The rewrite must be local to the emission of the method's generic parameter — i.e. in IlxGen's BuildGenericParameter/constraint-signature path, not stored back.
5. Preserve trait-constraint solutions. If a constraint is MayResolveMember(TTrait(...)), its TTrait carries a slnCell (see Remap.fs:326–371). In the realsig+ class?method case the method typar is a distinct quantifier whose trait solution must be re-derived or re-keyed. Either (a) do not copy slnCell at all (emit the constraint as unresolved and let the consumer re-solve against the method typar) or (b) use remapTraitInfo with removeTraitSolutions = true and re-resolve. (Option (a) is the minimal fix; the trait machinery is downstream of the class/method boundary anyway.)
6. Do not re-write the TyconRef/Val maps — they are identity-preserved in the realsig+ case.
Minimal fix in one function: In the single place in IlxGen.fs that, for each Typar in meth.Tps, builds the MetadataBuilder.DefineGenericParameter constraint argument, wrap the ty payload with a remapTypeAux-based substitution over the class?method TyparMap built from the method's enclosing type's ctps @ mtps split. That is a one-function change; it does not touch the TAST, does not touch copyTypar, does not touch ConstraintSolver.fs, and does not break the checker's invariants (the class typar's Typar.Constraints remain intact for the class's own members; the rewrite is local to the method emission).
Substitution sketch (what the fix looks like, for the record)
// In IlxGen.fs, at the point where a generic method's parameter constraint is emitted:
let emitMethodParamConstraint (methodTps : Typar list) (classTps : Typar list) (cs : TyparConstraint list) =
    let mkRenames =
        methodTps, classTps
        ||> List.zip
        |> List.map (fun (mtp, ctp) -> (ctp, TType_var(mtp, nullnessFree)))
    let remap = { emptyRemap with tpinst = mkRenames }
    cs
    |> List.map (function
        | TyparConstraint.CoercesTo(ty, m)       -> TyparConstraint.CoercesTo(remapTypeAux remap ty, m)
        | TyparConstraint.DefaultsTo(p, ty, m)   -> TyparConstraint.DefaultsTo(p, remapTypeAux remap ty, m)
        | TyparConstraint.IsEnum(ty, m)          -> TyparConstraint.IsEnum(remapTypeAux remap ty, m)
        | TyparConstraint.IsDelegate(a, r, m)    -> TyparConstraint.IsDelegate(remapTypesAux remap a, remapTypeAux remap r, m)
        | TyparConstraint.SimpleChoice(tys, m)   -> TyparConstraint.SimpleChoice(remapTypesAux remap tys, m)
        | other                                   -> other)
This is the same shape as remapTyparConstraintsAux (TypedTreeOps.Remap.fs:305–324), applied with the tpinst of class?method. The only difference from the TAST-level rewrite is where it is invoked: at IL emission, with the method typar's fresh identity, and not written back to the Typar object (no SetConstraints). That is the semantic invariant that makes it safe.
TL;DR
- Q1 — stamp identity: yes, sufficient to identify sites (typarEq, Stamped).
- Q2 — constraints are rewritable TType trees: yes, remapTyparConstraintsAux exists and is the right walk.
- Q3 — TLR/TAST phase: not safe / not supported. The realsig+ representation deliberately shares the class typar with the helper and repackages the fHat type; the "method typar" is created later by IlxGen, not by TLR. Rewriting constraints to point at a typar that is not (yet) a bound quantifier of the TAST node you're editing breaks well-scopedness, orphans trait-solution cells (keyed by original stamps), and corrupts ConstraintSolver.fs's solution tables.
- Q4 — alpha-rename only: only if the method typar is a bound quantifier in the same TAST — which it is not, in this pipeline. So the rewrite is not a pure alpha-rename at the TAST level.
- Q5 — codegen fix: localized, single-site rewrite in IlxGen.fs at the generic-parameter emission, TyparMap-based class?method substitution over the constraint payloads, without writing back to Typar.Constraints. One-function change; preserves all checker invariants.
