Verified. The fact that decides the whole plan is confirmed, and it points the other way from my last tentative guess.
The fact
In codegen, the choice of (a) class-level member vs module-level static, and (b) whether to split the val's typars into class-tyvars (ctps) + method-tyvars (etps) is made at one dispatch, and it keys only on Val.MemberInfo.IsSome — not on the shape of the public Val.Type:
// IlxGen.fs:1746-1752  (ComputeStorageForValWithValReprInfo)
match GetValReprTypeInFSharpForm ... with
| [], [], returnTy, _ when not vref.IsMember ->
    ComputeStorageForFSharpValue ...                              // static field
| _ ->
    match vref.MemberInfo with
    | Some memberInfo when not vref.IsExtensionMember ->
        ComputeStorageForFSharpMember cenv valReprInfo memberInfo vref m   // <-- SPLIT path
    | _ ->
        ComputeStorageForFSharpFunctionOrFSharpExtensionMember ...         // <-- NO split
- IsMember is defined as x.MemberInfo.IsSome — TypedTree.fs:3094. It is not derived from the type shape.
- The split path (ComputeStorageForFSharpMember ? GetMethodSpecForMemberVal) does the split with ctps, mtps = List.splitAt numParentTypars tps — IlxGen.fs:1490 — but it first does parentTcref = vref.DeclaringEntity — IlxGen.fs:1483 ? TypedTree.fs:3256-3259, which throws for a val with no parent.
- The no-split path computes numEnclosingTypars = CountEnclosingTyparsOfActualParentOfVal, which returns 0 when not v.IsMember — FreeVars.fs:658-664 — i.e. all typars stay method-typars.
Consequence (this is the crux)
The fHat that TLR creates is exactly a member-less val: mkLocalNameTypeArity builds it via Construct.NewVal(..., ParentNone) — InnerLambdasToTopLevelFuncs.fs:90. So every fHat falls into the no-split, module-level branch.
Therefore: giving the fHat a "member-shaped" public TType does nothing. The split is hard-gated on MemberInfo.IsSome, and the only way to reach it is to set MemberInfo, which changes IsMember + the parent/public shape — exactly the "passing in DeclaringEntity" change you said older compilers can't consume and that you don't want. So "rework the typed-tree shape of the fHat's public type" is not the route.
But the good news, which resolves the worry "how do I get the hosting class in there": you don't have to store it in the Val at all. The hosting class is already eenv.cloc at the moment the fHat's storage is computed. The realsig+ effectiveCloc already selects the class over the module:
// IlxGen.fs:10675-10687
if cenv.g.realsig then
    cloc            // the type that "originated the closure" — already the class
else
    eenv.moduleCloc
and AllocValReprWithinExpr calls ComputeAndAddStorageForLocalValWithValReprInfo (... ) effectiveCloc v eenv — IlxGen.fs:10689-10693 — so the class is on the stack, as the cloc argument, right at the dispatch that is mis-routed.
What this means for the plan
The single missing capability is a new branch at ComputeStorageForValWithValReprInfo: "realsig+ && top-level && non-member && cloc is a generic class ? emit as a class-level method, split the leading |cloc.TypeParams| typars as ctps." It reuses the same List.splitAt ctps.Length algorithm as IlxGen.fs:1490, driven by the class in cloc rather than by a MemberInfo. This:
- touches no Val field ? no pickling/parent/TryDeclaringEntity change, which is your non-negotiable;
- leaves the public Val.Type shape alone (the split happens at emission, so the observable class-level method still reads as a member of the class);
- is a codegen-local addition, not a TLR-data-transport problem.
The TLR-side ep_ctps/ep_etps split and the two-tier call-site rewrite are necessary but not sufficient on their own: without this codegen branch, codegen throws them away (member-less ? numEnclosingTypars=0).
